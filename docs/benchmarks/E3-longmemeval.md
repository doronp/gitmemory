# E3 ship gate — LongMemEval

**Verdict: passed.** 470 instances, four compaction modes, all 14 calibration
checks green. Generated by `python -m bench` at the commit this file lands in;
the tables below are that command's output verbatim, prepended with what they do
and do not support.

    bench/fetch_longmemeval.sh          # 277 MB, SHA-256 pinned, opt-in
    python -m bench --dataset "$GITMEMORY_LONGMEMEVAL"

Runtime 2m02s on one laptop core. Nothing is cached between runs; the index is
built from the transcript bytes for every instance and every mode.

## What the arms are

| Arm | What it is |
|---|---|
| `candidate` | gitmemory's BM25 index over the whole transcript |
| `none` | retrieves nothing — the floor |
| `shuffled` | the same retriever, asked a *different* instance's question |
| `reference` | the oracle: reads the ground-truth offsets, bypasses retrieval |
| `live_context` | the same retriever, window restricted to offsets at or after the last compaction boundary — what the agent can still see unaided |

`dense` (model2vec) and `rerank` (flashrank) did not run: their dependencies are
not installed here, which the report says on its own front page. **So this run
does not show that BM25 beats embeddings.** It shows BM25 beats nothing, beats a
foreign query, and beats the live window. Those are three different claims and
only the third is the product's.

## The headline

Under `after_evidence` — the only arrangement where the compaction boundary
actually falls between the evidence and the end of the transcript, so a live
context window has genuinely lost it:

| Arm | Turn recall | Turn MRR |
|---|---|---|
| `candidate` | **0.7456** | **0.6209** |
| `live_context` | 0.0000 | 0.0000 |

That zero is the point. The evidence is behind the boundary, so the window
cannot reach it at any k, and the index reaches it three times in four.

## Four things this run does not let you say

**1. The oracle does not score 1.0 on sessions, and that is the dataset.**
`reference` turn recall is exactly 1.0 — the apparatus check requires it — but
its *session* recall is 0.9687. Verified cause: 32 of 470 instances list an
answer session that contains no `has_answer` turn at all (45 of 890 answer
sessions), so the offsets the oracle reads cannot land in it. That is a property
of LongMemEval, not of the harness, which is why the apparatus gate is on turn
recall.

This page used to tell you to treat every session-recall number on it as
"capped near 0.97", and that was wrong. 0.9687 is the oracle's mean over all
470 instances; it is not a ceiling on any cell, and the page contradicts it in
plain sight — **38 of the 140 per-type cells below sit above 0.97, and 8 of
them are exactly 1.0000**, `candidate` arms among them. The 32 unreachable
instances depress a whole-set mean and are silent in a breakdown that does not
contain them. Read a session-recall number against the `reference` cell in its
own row, which is the oracle under the same slice, rather than against 1.0. On
this run no `candidate` cell exceeds its own row's oracle (0 of 28 slices), but
nothing structurally forbids it: the oracle retrieves by turn offset and a text
retriever can return a session the offsets cannot reach.

**2. Under `before_evidence`, the live window *beats* the index** — 0.7893 vs
0.7456 turn recall. Not an anomaly: walling off everything before the evidence
also walls off the distractors, so the restricted arm searches an easier
haystack. This is exactly why `CLAIM_MODE` is `after_evidence` and not "whichever
mode looks best". A benchmark that picked its own mode would have reported the
0.7893 as a gitmemory number.

**3. `no_leakage` passes with little room.** `shuffled − none = 0.0350` against a
`LEAK_MARGIN` of 0.05. The control arm is not at zero, because a foreign question
of the same `question_type` still shares template words with the corpus. 0.0350
clears the bound; it does not clear it comfortably, and a fixture change that
adds shared vocabulary would push it over.

**4. `p = 2.225e-308` is a floor, not a measurement.** `1 - normal_cdf(z)`
underflows to exactly 0.0 around z = 38 and 470 paired instances reach it. The
value printed is `sys.float_info.min`. Read it as "smaller than a double can
say", not as a number.

## And one about the corpus itself

The transcripts are LongMemEval sessions rendered into Claude Code JSONL by
`bench/synth.py`. They are structurally faithful — real block shapes, real
compaction summaries, byte offsets that tile — but they are synthesised. This
measures retrieval over agent-transcript *structure*. It does not measure
retrieval over a real agent's transcript, and no number here should be quoted as
if it did.
